🧭 1. Principes directeurs
Voici les règles qui guident une architecture documentaire professionnelle :

1. Un README = un point d’entrée, pas un manuel
Il oriente, il ne détaille pas.

2. La documentation détaillée doit être centralisée
Un seul endroit pour les explications longues, les guides, les schémas, les protocoles.

3. Le moteur quantitatif doit être isolé
Pour que les futurs contributeurs sachent où regarder.

4. Les interfaces, exports, rituels et annexes doivent être séparés
Pour éviter la confusion entre “moteur” et “écosystème”.

5. La racine doit rester lisible
Pas plus de 10–12 fichiers visibles.

🧩 3. Le rôle de chaque README
Voici la logique que tu vas appliquer partout :

README.md (racine)
Le “guide Michelin” du projet.
Il doit contenir :

description du projet

architecture globale

comment installer

comment exécuter

où trouver la documentation détaillée

où se trouve le moteur quantitatif

où se trouvent les interfaces

où se trouvent les exports

où se trouvent les rituels/documentation interne

README des dossiers quantitatifs
(data, indicators, backtest, strategy, utils, modules/quant)

Ils doivent répondre à :

“Que contient ce dossier ?”

“Comment l’utiliser ?”

“Quels sont les fichiers importants ?”

“Comment s’intègre-t-il dans le moteur quantitatif ?”

README des interfaces
(interface, interface_pilotage)

Ils doivent répondre à :

“Quels dashboards existent ?”

“Comment les lancer ?”

“À quoi servent-ils ?”

README des exports
(exports)

Ils doivent répondre à :

“Quels fichiers sont générés ?”

“Par quels modules ?”

“Comment les utiliser ?”

README de documentation_md
Il doit expliquer :

que ce dossier contient les rituels, annexes, scripts d’automatisation

que ce n’est pas la documentation technique

comment naviguer dans cet espace
