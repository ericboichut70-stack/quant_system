    Ce document décrit en profondeur la couche indicateurs du moteur quantitatif. Il complète le README du dossier indicators/ en offrant une vue technique, détaillée et structurée.

    🧭 1. Rôle de la Couche Indicateurs

    La couche indicators/ transforme les données brutes en features exploitables par:

    • les modules quantitatifs (modules/quant/)
    • la stratégie (strategy/)
    • le backtest (backtest/)

    Elle constitue la seconde couche du pipeline, juste après data/.

    🧱 2. Types d’Indicateurs

    2.1 Indicateurs de Base

    • EMA, SMA

    • RSI

    • ATR
    • Volumes
    • Variations, dérivées
    • Normalisations

    2.2 Indicateurs Avancés

    • énergie (phoebus_energy)

    • pivots UT

    • signaux composites
    • volatilité dérivée
    • signaux multi‑timeframes

    2.3 Indicateurs Structurels

    Utilisés par les modules quantitatifs :

    • swings
    • zones clés
    • impulsions
    • compressions

    🔧 3. Pipeline des Indicateurs

    Le pipeline suit les étapes suivantes :

    1. Préparation
    2. alignement temporel
    3. gestion des NaN

    4. normalisation

    5. Calcul

    6. application des formules
    7. calcul vectorisé

    8. gestion des décalages

    9. Enrichissement

    10. signaux booléens
    11. signaux multi‑niveaux

    12. signaux composites

    13. Validation

    14. absence de lookahead
    15. cohérence temporelle
    16. compatibilité avec les modules

    📂 4. Structure du Dossier

    Le dossier peut contenir :

    • base_indicators.py
    • phoebus_energy.py
    • ut_pivots.py
    • normalization.py
    • signal_utils.py
    • index.md (documentation locale)

    🧪 5. Tests et Validation

    Les tests doivent vérifier :

    • la cohérence des valeurs
    • l’absence de lookahead bias
    • la stabilité numérique
    • la compatibilité avec les modules quantitatifs
    • la reproductibilité

    🧭 6. Intégration avec les autres couches

    data/ → indicators/ → modules/quant/ → strategy/ → backtest/

    Les indicateurs sont strictement en amont des modules quantitatifs.

    🎼 7. Pivots UT — État actuel & Évolution Phase 3.1

    Les pivots UT constituent un indicateur structurel utilisé pour repérer :

    les zones d’équilibre

    les zones d’excès

    les zones de retournement potentiel

    les zones de compression ou d’expansion

    Deux systèmes coexistent actuellement dans le projet :

    Ballistic Pivots (système historique, opérationnel)

    UTPivots7 (système Phase 3.1, expérimental)

    Cette coexistence est volontaire : elle permet de tester l’évolution sans perturber le moteur existant.

    🎯 7.1 Système historique — Ballistic Pivots

    Le système Ballistic repose sur :

    une régression polynomiale (centre de gravité)

    l’écart‑type des résidus (sigma)

    des multiplicateurs dérivés du ratio d’or

    une structure 3–1–3 :

    S1, S2, S3, S4

    Pivot central

    R1, R2, R3, R4

    Ce système est actuellement utilisé dans les modules existants.

    Il reste la référence opérationnelle tant que les backtests Phase 3 n’ont pas validé une alternative.

    🎼 7.2 Système Phase 3.1 — UTPivots7 (Do–Ré–Mi–Fa–Sol–La–Si)

    Le système UTPivots7 est une évolution expérimentale, conçue pour :

    • simplifier la structure
    • améliorer la lisibilité
    • réduire la volatilité des niveaux
    • rester fidèle à la logique 3–1–3
    • permettre une future simplification (5 pivots ou 3 pivots)

    Niveaux

    • P_Do : support extrême
    • P_Re : support intermédiaire
    • P_Mi : support proche du centre
    • P_Fa : pivot central
    • P_Sol : résistance proche du centre
    • P_La : résistance intermédiaire
    • P_Si : résistance extrême

    Formules institutionnelles

    Soit :

    • High_ref : plus haut du range de référence
    • Low_ref : plus bas du range de référence
    • Mid_ref : (High_ref + Low_ref) / 2
    • D : (High_ref - Low_ref) / 6

    Alors :

    • P_Do = Mid_ref − 3D
    • P_Re = Mid_ref − 2D
    • P_Mi = Mid_ref − D
    • P_Fa = Mid_ref
    • P_Sol = Mid_ref + D
    • P_La = Mid_ref + 2D
    • P_Si = Mid_ref + 3D

    Ce système est simple, stable, lisible, et parfaitement adapté aux tests exploratoires.

    🧪 7.3 Tests & Comparaison

    Deux types de tests sont en place :

    ✔️ Tests unitaires vérification du nombre de niveaux

    vérification de la cohérence interne

    absence d’erreur d’exécution

    ✔️ Tests comparatifs comparaison du pivot central Ballistic vs UTPivots7

    comparaison des structures

    analyse visuelle via notebook dédié

    Ces tests permettent d’évaluer la pertinence du système UTPivots7 sans perturber l’existant.

    🧭 7.4 Statut actuel

    Ballistic Pivots : système officiel, utilisé dans le moteur

    UTPivots7 : système expérimental, non intégré au moteur

    Aucune bascule automatique n’est prévue à ce stade

    Aucune dépendance n’existe entre les deux systèmes

    Cette séparation garantit la stabilité du projet tout en permettant l’exploration.

    🔮 7.5 Perspectives Phase 3

    Les prochaines étapes prévues :

    validation empirique de UTPivots7

    comparaison multi‑UT

    intégration optionnelle (si validée)

    éventuelle simplification (5 pivots ou 3 pivots)

    documentation finale Phase 3.2

    🔥 8. Phoebus Énergie — Phase 3.2 (Ouverture)

    La Phase 3.2 introduit l’évolution expérimentale du module Phoebus Énergie, un indicateur avancé destiné à mesurer :

    • l’intensité directionnelle du marché
    • la dynamique interne des impulsions
    • la dissipation ou l’accumulation d’énergie
    • les transitions entre phases d’expansion et de compression

    Cette évolution reste strictement expérimentale et n’a aucun impact sur le moteur existant tant qu’elle n’a pas été validée par les backtests.

    🎯 8.1 Positionnement institutionnel

    Phoebus Énergie appartient à la catégorie des indicateurs avancés, au même titre que :

    • les pivots UT
    • les signaux composites
    • les mesures de volatilité dérivée

    Il ne s’agit pas d’un oscillateur classique, mais d’un indicateur structurel, conçu pour :

    • capturer la dynamique interne du prix
    • détecter les zones de tension énergétique
    • anticiper les ruptures de structure
    • qualifier la force d’un mouvement

    L’objectif n’est pas de produire un signal d’achat/vente, mais une mesure neutre, exploitable par les modules quantitatifs.

    🧩 8.2 Objectifs techniques de la Phase 3.2

    La Phase 3.2 vise à :

    1. Clarifier la définition mathématique de l’énergie (version institutionnelle)
    2. Séparer proprement :
    3. l’énergie brute
    4. l’énergie normalisée
    5. l’énergie dérivée
    6. Créer une structure de module propre dans indicators/phoebus_energy.py
    7. Préparer les tests unitaires pour valider :
    8. la cohérence temporelle
    9. l’absence de lookahead
    10. la stabilité numérique
    11. Documenter l’indicateur sans l’intégrer au moteur
    12. Préparer un notebook d’analyse visuelle (non obligatoire mais recommandé)

    Aucune intégration dans les modules quantitatifs n’est prévue à ce stade.

    🧱 8.3 Périmètre de la Phase 3.2

    La Phase 3.2 se limite à :

    • définir la formule institutionnelle
    • structurer le module
    • produire un prototype testable
    • documenter l’indicateur
    • valider la cohérence interne

    Elle n’inclut pas :

    • l’intégration dans le moteur
    • l’utilisation dans la stratégie
    • l’utilisation dans les backtests
    • la calibration automatique
    • la génération de signaux

    Ces étapes appartiendront à la Phase 3.3 ou ultérieure.

    ⚠️ 8.4 Contraintes et risques

    • Neutralité scientifique : éviter toute interprétation subjective
    • Stabilité numérique : éviter les explosions de valeurs
    • Cohérence multi‑UT : l’énergie doit rester comparable entre UT
    • Simplicité : éviter les formules ésotériques ou non reproductibles
    • Non‑intrusion : ne pas perturber les modules existants

    Ces contraintes garantissent que Phoebus Énergie reste un indicateur institutionnel, reproductible et exploitable.

    🧭 8.6 Statut actuel

    Phoebus Énergie (Phase 3.2) est :

    • en cours de définition
    • non intégré au moteur
    • non utilisé par les modules
    • strictement expérimental
    • documenté mais inactif

    Il constitue une brique exploratoire destinée à enrichir la compréhension structurelle du marché.

    🧬 8.7 Versions et coexistence

    Deux versions de Phoebus Énergie coexistent désormais dans le projet :

    • Phoebus Énergie v1 — Version historique

    Fichier : phoebus_energy_v1.py
    Statut : stable, complète, non modifiée
    Rôle :

    • analyse avancée
    • comparaison avec références externes
    • calibration
    • laboratoire d’expérimentation

    • Phoebus Énergie — Phase 3.2

    Fichier : phoebus_energy.py
    Statut : expérimental, institutionnel
    Rôle :

    • base neutre pour l’évolution
    • énergie brute reproductible
    • fondation pour les futures étapes (normalisation, dérivée, multi‑UT)

    Principe de coexistence

    Les deux versions sont maintenues en parallèle afin de :

    • préserver le travail historique
    • garantir la stabilité du projet
    • permettre une évolution progressive
    • éviter toute perturbation du moteur existant

    Aucune des deux versions n’est supprimée ou remplacée.
    La Phase 3.2 construit une base institutionnelle pour les futures évolutions, sans altérer la version historique.

    🔧 8.8 Énergie normalisée — Phase 3.2.1

    L’énergie normalisée constitue la seconde brique du système Phoebus Énergie.
    Elle vise à rendre l’énergie brute comparable entre :

    • unités de temps
    • actifs
    • régimes de volatilité

    Définition institutionnelle

    L’énergie normalisée est définie comme :

    [ E_n(t) = \frac{E_b(t)}{ATR(t)} ]

    où :

    • (E_b(t)) est l’énergie brute
    • (ATR(t)) est l’Average True Range (fenêtre 14 par défaut)

    Cette normalisation :

    • neutralise l’effet de l’échelle du prix
    • neutralise l’effet de la volatilité locale
    • garantit une mesure UT‑agnostique
    • reste strictement sans lookahead

    Statut

    • version expérimentale
    • non intégrée au moteur
    • base institutionnelle pour les futures étapes

    🔄 8.9 Énergie dérivée — Phase 3.2.2

    L’énergie dérivée constitue la troisième brique du système Phoebus Énergie.
    Elle mesure la variation de l’énergie normalisée dans le temps, permettant d’identifier:

    • accélérations
    • décélérations
    • ruptures de régime
    • transitions structurelles

    Définition institutionnelle — Phase 3.2.2

    [ E_d(t) = E_n(t) - E_n(t-1) ]

    où :

    • (E_n(t)) est l’énergie normalisée
    • aucune moyenne glissante n’est appliquée
    • aucune transformation non linéaire n’est introduite

    Cette mesure reste :

    • locale
    • directionnelle
    • sans lookahead
    • compatible avec les modules quantitatifs

    Statut — Phase 3.2.2

    • version expérimentale
    • non intégrée au moteur
    • fondation pour les futures analyses structurelles

    🧭 8.10 Chaîne énergétique complète

    Le système Phoebus Énergie Phase 3.2 repose désormais sur trois briques :

    1. Énergie brute

    [ E_b(t) = |P(t) - P(t-1)| ] 2. Énergie normalisée

    [ E_n(t) = \frac{E_b(t)}{ATR(t)} ] 3. Énergie dérivée

    [ E_d(t) = E_n(t) - E_n(t-1) ]

    Cette chaîne est :

    • neutre
    • reproductible
    • UT‑agnostique
    • compatible multi‑actifs
    • strictement sans lookahead

    Elle constitue la base institutionnelle de la Phase 3.3.

    🧩 8.11 Phase 3.3 — Intégration optionnelle (cadrage institutionnel)

    La Phase 3.3 ne vise pas à intégrer Phoebus Énergie dans le moteur opérationnel.
    Elle définit les conditions institutionnelles nécessaires pour qu’une intégration future soit envisageable, sans perturber la stabilité du système.

    Cette phase est strictement exploratoire et ne modifie aucun module existant.

    🎯 Objectifs

    • Définir les critères d’intégration potentielle de Phoebus Énergie.
    • Définir les tests de robustesse nécessaires avant toute intégration.
    • Définir les points de contact possibles avec les modules quantitatifs.
    • Garantir la neutralité scientifique et la reproductibilité.

    🧱 Contraintes institutionnelles

    Tout indicateur candidat à l’intégration doit respecter :

    • absence de lookahead
    • stabilité numérique
    • cohérence multi‑UT
    • cohérence multi‑actifs
    • faible sensibilité aux outliers
    • faible dépendance aux paramètres
    • reproductibilité totale
    • neutralité scientifique

    Phoebus Énergie Phase 3.2 respecte déjà une partie de ces contraintes, mais nécessite une validation approfondie.

    🔬 Tests de robustesse à définir

    La Phase 3.3 consiste à définir les tests suivants :

    1. Test de variance glissante
      Vérifie la stabilité de la dispersion de l’énergie dans le temps.

    2. Test de stabilité de distribution
      Analyse la forme de la distribution (skewness, kurtosis, dérive).

    3. Test de corrélation croisée
      Vérifie l’absence de corrélations artificielles avec le prix ou d’autres indicateurs.

    4. Test de sensibilité aux outliers
      Mesure l’impact des points extrêmes sur les trois énergies.

    5. Test de cohérence multi‑UT
      Vérifie la stabilité des comportements entre M1, M5, M15, H1.

    6. Test de cohérence multi‑actifs
      Vérifie la robustesse sur devises, indices, crypto, matières premières.

    7. Test de stabilité temporelle
      Vérifie la robustesse sur plusieurs années et plusieurs régimes de marché.

    Ces tests ne sont pas implémentés en Phase 3.3 :
    la phase consiste uniquement à les définir.

    🧭 Points de contact potentiels avec le moteur

    Phoebus Énergie pourrait, à terme, alimenter :

    • un module de détection de compression/expansion
    • un module de détection de ruptures structurelles
    • un module de qualité de mouvement
    • un module de filtrage des signaux
    • un module de classification des régimes

    Aucune intégration n’est prévue en Phase 3.3.

    📌 Statut

    • Phase strictement exploratoire
    • Aucun impact sur le moteur
    • Aucun signal produit
    • Aucun module modifié
    • Préparation institutionnelle pour une éventuelle Phase 3.4

    🧪 8.12 Phase 3.4 — Validation expérimentale

    La Phase 3.4 constitue la première étape de validation expérimentale du système Phoebus Énergie.
    Elle ne modifie pas le moteur et n’intègre aucun signal opérationnel.
    Elle vise à évaluer la robustesse empirique des trois briques énergétiques sur un ensemble d’actifs, d’unités de temps et de périodes historiques.

    🎯 Objectifs

    • Exécuter les tests de robustesse définis en Phase 3.3.
    • Évaluer la stabilité statistique des trois énergies.
    • Identifier les comportements anormaux, ruptures ou sensibilités excessives.
    • Déterminer si une Phase 3.5 (pré‑intégration) est justifiée.

    🔬 Méthodologie

    La validation expérimentale repose sur :

    1. Échantillons multi‑actifs
    2. devises
    3. indices
    4. crypto

    5. matières premières

    6. Échantillons multi‑UT

    7. M1, M5, M15, H1

    8. Échantillons multi‑régimes

    9. volatilité faible
    10. volatilité élevée
    11. tendances prolongées

    12. ranges prolongés

    13. Tests statistiques

    14. variance glissante
    15. stabilité de distribution
    16. corrélation croisée
    17. sensibilité aux outliers
    18. cohérence multi‑UT
    19. cohérence multi‑actifs
    20. stabilité temporelle

    📌 Statut

    • Phase expérimentale
    • Aucun impact sur le moteur
    • Aucun signal produit
    • Préparation à une éventuelle Phase 3.5

    🧱 8.13 Phase 3.5 — Pré‑intégration

    La Phase 3.5 constitue l’étape de pré‑intégration du système Phoebus Énergie.
    Elle intervient uniquement si la Phase 3.4 a démontré une robustesse suffisante sur l’ensemble des tests statistiques, multi‑UT, multi‑actifs et multi‑régimes.

    Cette phase ne fusionne pas encore Phoebus Énergie dans le moteur, mais prépare l’intégration en définissant les interfaces, les invariants, les garde‑fous et les conditions d’activation.

    🎯 Objectifs

    • Définir l’interface d’intégration potentielle dans le moteur.
    • Définir les invariants que l’indicateur doit respecter en production.
    • Définir les garde‑fous empêchant toute dérive ou instabilité.
    • Définir les conditions d’activation (opt‑in, expérimental, sandbox).
    • Préparer la documentation technique d’intégration.

    🧩 Interfaces potentielles

    Phoebus Énergie pourrait être exposé via :

    • une classe EnergyModule indépendante
    • un namespace energy dans le moteur
    • un wrapper d’accès unifié (multi‑UT, multi‑actifs)
    • un point d’entrée optionnel dans les pipelines quantitatifs

    Aucune interface n’est implémentée en Phase 3.5.

    🧱 Invariants institutionnels

    Tout module candidat à l’intégration doit garantir :

    • absence totale de lookahead
    • stabilité numérique (pas de NaN, pas d’infini)
    • vectorisation complète
    • coût CPU maîtrisé
    • comportement stable sur données manquantes
    • comportement stable sur données bruitées
    • comportement stable sur données extrêmes

    🛡️ Garde‑fous

    Avant toute intégration, Phoebus Énergie doit :

    • passer les tests de robustesse Phase 3.4
    • démontrer une stabilité multi‑UT
    • démontrer une stabilité multi‑actifs
    • démontrer une stabilité temporelle
    • ne pas introduire de dépendance externe
    • ne pas modifier les modules existants

    📌 Statut

    • Phase préparatoire
    • Aucun code intégré au moteur
    • Aucun signal produit
    • Préparation institutionnelle pour la Phase 3.6 (intégration contrôlée)

    🧩 8.14 Phase 3.6 — Intégration contrôlée

    La Phase 3.6 constitue la première étape d’intégration potentielle du système Phoebus Énergie dans le moteur quantitatif.
    Cette intégration est strictement contrôlée, réversible, et sans impact sur les modules existants tant que toutes les conditions institutionnelles ne sont pas validées.

    🎯 Objectifs

    • Introduire Phoebus Énergie dans le moteur sous forme d’option inactive par défaut.
    • Définir un wrapper d’accès garantissant la neutralité et la reproductibilité.
    • Implémenter les invariants institutionnels définis en Phase 3.5.
    • Mettre en place les garde‑fous empêchant toute dérive ou instabilité.
    • Garantir une coexistence propre entre la version historique et la version Phase 3.2.

    🧱 Invariants d’intégration

    Avant activation, Phoebus Énergie doit respecter :

    • stabilité numérique (aucun NaN, aucun infini)
    • absence totale de lookahead
    • comportement stable sur séries courtes
    • cohérence multi‑UT
    • cohérence multi‑actifs
    • coût CPU maîtrisé
    • reproductibilité totale

    Ces invariants sont vérifiés automatiquement par les tests Phase 3.5.

    🛡️ Garde‑fous

    L’intégration contrôlée impose :

    • un wrapper isolé (EnergyModule)
    • aucune modification des modules existants
    • activation manuelle explicite
    • logs institutionnels en cas d’anomalie
    • désactivation automatique en cas de violation d’invariant

    🧩 Architecture d’intégration

    Phoebus Énergie est exposé via :

    modules/
quant/
energy/
energy_module.py   ← wrapper institutionnel

    Le moteur ne consomme jamais directement PhoebusEnergy.
    Il passe uniquement par le wrapper, garantissant :

    • neutralité
    • stabilité
    • traçabilité
    • réversibilité

    📌 Statut

    • Intégration optionnelle
    • Inactive par défaut
    • Aucun impact sur les signaux
    • Préparation à la Phase 3.7 (activation expérimentale)

    🚦 8.15 Phase 3.7 — Activation expérimentale

    La Phase 3.7 constitue la première activation expérimentale de Phoebus Énergie dans un contexte moteur, sur un périmètre strictement contrôlé.

    🎯 Objectifs

    • Activer Phoebus Énergie via le wrapper institutionnel (EnergyModule).
    • Limiter l’activation à un environnement expérimental ou sandbox.
    • Observer le comportement du moteur avec et sans l’indicateur.
    • Mesurer l’impact sur :
    • la stabilité des signaux
    • les performances des stratégies
    • la sensibilité aux régimes de marché

    🧱 Périmètre d’activation

    • Environnement : sandbox / expérimental uniquement
    • Stratégies : sous‑ensemble limité, documenté
    • Actifs : sélection restreinte (devises / indices / crypto)
    • UT : ensemble prédéfini (ex. M5, M15, H1)

    Aucune activation globale en production n’est prévue en Phase 3.7.

    🧪 Méthodologie

    • lancer des backtests comparatifs :
    • moteur sans Phoebus Énergie
    • moteur avec Phoebus Énergie activée
    • comparer :
    • la stabilité des résultats
    • la sensibilité aux paramètres
    • la robustesse des stratégies

    📌 Statut

    • Phase expérimentale, non productive
    • Activation encadrée par configuration
    • Retour possible à l’état sans Phoebus Énergie à tout moment
