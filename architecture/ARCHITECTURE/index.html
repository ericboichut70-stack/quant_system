    # 🧭 Architecture Globale du Projet

    Ce document présente la vision d’ensemble de l’architecture du projet, en décrivant les couches principales, leurs responsabilités, leurs interactions et les principes qui guident la conception du système.

    Il complète system_flow.md en offrant une vue plus structurée, plus textuelle et plus conceptuelle.

    🧱 1. Principes d’Architecture

    Le projet repose sur plusieurs principes fondamentaux :

    ✔️ Modularité

    Chaque composant est isolé dans un dossier dédié :

    • data/
    • indicators/
    • modules/quant/
    • strategy/
    • backtest/
    • interface/
    • interface_pilotage/

    ✔️ Séparation des responsabilités

    Chaque couche a un rôle clair :

    • données → indicateurs → modules quantitatifs → stratégie → backtest → exports → interfaces

    ✔️ Extensibilité

    L’architecture permet d’ajouter :

    • de nouveaux indicateurs
    • de nouveaux modules quantitatifs
    • de nouvelles stratégies
    • de nouvelles interfaces
    • de nouveaux exports

    sans casser l’existant.

    ✔️ Documentation centralisée

    Toute la documentation technique vit dans docs/.

    🧩 2. Couches du Système

    2.1 Données (data/)

    • ingestion
    • nettoyage
    • normalisation
    • validation
    • formats standardisés (OHLCV)

    2.2 Indicateurs (indicators/)

    • EMA, RSI, pivots
    • signaux techniques
    • features enrichies
    • transformations mathématiques

    2.3 Modules Quantitatifs (modules/quant/)

    • structure de marché
    • volatilité
    • orderflow
    • signaux avancés
    • optimisation
    • pré‑trade
    • radar & scanning

    2.4 Stratégie (strategy/)

    • règles d’entrée/sortie
    • gestion du risque
    • orchestration des signaux
    • logique décisionnelle

    2.5 Backtest (backtest/)

    • simulation historique
    • métriques de performance
    • journaux d’exécution
    • validation des stratégies

    2.6 Exports (exports/)

    • rapports
    • visuels
    • CSV / JSON
    • audits
    • badges / scoring

    2.7 Interfaces (interface/, interface_pilotage/)

    • dashboards Streamlit
    • outils de pilotage
    • interfaces audio
    • CLI
    • simulateurs internes

    🔄 3. Flux d’Information

    Le flux suit une direction claire :

    Données → Indicateurs → Modules Quant → Stratégie → Backtest → Exports → Interfaces

    Chaque couche enrichit la précédente.

    🧬 4. Dépendances

    • indicators/ dépend de data/
    • modules/quant/ dépend de indicators/
    • strategy/ dépend de modules/quant/
    • backtest/ dépend de strategy/
    • interface/ dépend de exports/

    Les dépendances sont unidirectionnelles, jamais circulaires.

    🧭 5. Vision Long Terme

    L’architecture est conçue pour accueillir :

    • du machine learning
    • des modèles prédictifs
    • des stratégies multi‑actifs
    • du trading en temps réel
    • des API brokers
    • des dashboards avancés
    • des modules pédagogiques évolutifs

    6. Mini-cartes des grandes zones du système

    <!-- markdownlint-disable MD029

    1. Vue d’ensemble du projet À partir de root_level.txt, ton projet se structure clairement en grandes zones fonctionnelles :

    Cœur quant / logique métier :
    modules, src, strategy, indicators, eurusd, utils, backtest, exports, interface, interface_pilotage

    Données & résultats :
    data, logs, replays, reports, notebooks, progression

    Documentation & rituels :
    docs, documentation, documentation_md, ARCHITECTURE.md, MANIFEST_TECHNIQUE.md, README*.md

    Infrastructure & outillage :
    .venv, config, scripts, structure_*.txt, generate_audit.ps1, requirements.txt, run_test.py

    Tests & qualité :
    tests, tests_level.txt, tous les test_*.py dans modules

    C’est déjà une architecture de “système vivant” cohérente, pas un chaos.

    1. Mini-carte : zone modules

    2.1. Structure logique

    modules_level.txt montre un noyau modulaire très riche, orienté pédagogie, communauté, backtest et signaux.

    Mini-carte conceptuelle :

    text modules/ ├─ quant/ (moteur quant, logique cœur) ├─ utils/ (outils transverses) ├─ ...engine.py (backtest, certification, cohérence) ├─ ..._dashboard.py (interfaces de suivi) ├─ ..._mapper.py (mapping, FVG, POI, structure) ├─ ..._tracker.py (progression, objectifs) ├─ ..._storyline.py (narration, pédagogie) ├─ trading_api.py (pont vers exécution) ├─ test*.py (tests unitaires intégrés) └─ init.py

    2.2. Lecture structurelle

    Très bon point :
    Les test_*.py dans modules montrent une volonté de tester au plus près des composants.

    Modules clés pour le quant pur :
    backtest_engine.py, optimizer.py, orderflow_reader.py, order_blocks.py, signal_filter.py, signal_predictor.py, trend_detector.py, volatility_clustering.py, trading_api.py.

    Couches “méta” / pédagogiques :
    auto_mentor.py, community_, pedagogical_, season_*, tournament_hub.py, etc. → C’est ton “écosystème vivant”, la couche d’orchestration sociale et pédagogique.

    1. Mini-carte : zone tests

    3.1. Structure tests_level.txt :

    text tests/ ├─ demos/ ├─ unit/ ├─ test_*.py ├─ README.md └─ index.md

    3.2. Lecture structurelle Tests de haut niveau :
    test_energy_integration.py, test_strategy_core.py, test_backtest_runner.py → tests d’intégration / pipeline.

    Tests ML & robustesse :
    test_ml_*, test_feature_engineering.py, test_ml_robustness.py → très bon signal pour la future phase ML.

    Tests énergie / Phoebus :
    test_phoebus_energy.py, test_phoebus_energy_robustness.py, test_energy_module.py → parfait pour ton Phase 3.2.1.

    La présence de demos/ et unit/ laisse penser que tu as déjà prévu une séparation entre exemples pédagogiques et tests unitaires stricts.

    1. Mini-carte : zone docs

    4.1. Structure

    docs_level.txt :

    text docs/ ├─ achitecture/ (typo mais claire) ├─ dev_guides/ ├─ exports/ ├─ interfaces/ ├─ modules/ ├─ pedagogy/ ├─ quant_engine/ ├─ reference/ ├─ roadmap/ ├─ phase_*.md ├─ PHASE_3_PHOEBUS_ENERGIE.md ├─ AUDIT.md, TOC.md, README.md └─ onboarding.md

    4.2. Lecture structurelle

    Docs par couches :
    quant_engine/, modules/, interfaces/, exports/ → aligné avec l’architecture du code.

    Docs par phases :
    phase_1_architecture.md → phase_6_deep_learning.md
    → Ton système documentaire suit la progression du projet.

    Référentiel solide :
    reference/ (glossaire, principes, guidelines) → base parfaite pour un onboarding institutionnel.

    1. Mini-carte : zone config

    5.1. Structure

    config/ est ton registre institutionnel :

    text config/ ├─ bot_registry_.yaml / .md ├─ bot_manifest_, bot_release, bot_roadmap.yaml ├─ modules.yaml, module_registry.yaml ├─ user.yaml, feedback.yaml, flags.yaml, limits.yaml ├─ propfirms/.json └─ index.md 5.2. Lecture structurelle C’est ton “registre d’état” du système : versions, manifestes, validation, mémoire, roadmap, certificats.

    Lien direct avec ton rituel de clôture / transmission :
    les fichiers bot_registry_ et bot_roadmap_ sont déjà au niveau “institution”.

    1. Mini-carte : zone data

    6.1. Structure

    text data/ ├─ *.csv (or, UB, énergie, backtests, signaux) ├─ cleaned/eurusd/{H1,M1,M15} ├─ processed/eurusd/{H1,M1,M15} ├─ raw/eurusd/{H1,M1,M15} ├─ metadata/eurusd/{anomalies, cleaning_report, source} ├─ news_calendar/ ├─ predictability_scores/ └─ index.md, README.md

    6.2. Lecture structurelle

    Pipeline de données explicite :
    raw → cleaned → processed → signals_global.csv / backtest_results.csv.

    Traçabilité :
    metadata/eurusd/cleaning_report.md, anomalies.json, source.txt → tu as déjà la base d’un data lineage.
